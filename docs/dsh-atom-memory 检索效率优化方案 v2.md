# dsh-atom-memory 检索效率优化方案 v2（实测归因版）

> 本版取代 v1（`docs/dsh-atom-memory 检索效率优化方案.md`）。v1 的核心论断建立在未经验证的假设上，
> 本版所有优先级都由 `bench/stage_timing.py` 在一份真实生产库上的分阶段实测数据推导得出。

---

## 一、实测数据（归因基线）

测量环境：`bench/stage_timing.py --repeat 40`，Python 3.14.5 / Windows。
数据库：`~/.dsh/atom-memory/memory.db`，**1061 条 active 事实、单用户、13 个 scope、1072 行向量**。
全部为**预热后稳态**（模型已加载、页缓存已热）；重复 30–50 次取 p50。

### 1.1 retriever 内部分阶段

| 阶段 | p50 | 占 search_total |
|---|---|---|
| `_vector_knn` | **8.91 ms** | **71.9%** |
| `embed` | 1.51 ms | 12.2% |
| `_fetch_facts` | 0.66 ms | 5.3% |
| `_fts_search` | 0.58 ms | 4.7% |
| `_rerank` | 0.23 ms | 1.8% |
| `_scope_view` | 0.037 ms | 0.3% |
| `rrf_merge` | 0.027 ms | 0.2% |
| 未归因（胶水） | 0.45 ms | 3.6% |
| **search_total** | **12.40 ms** | 100% |

### 1.2 端到端与进程边界

| 层级 | p50 | 相对上一层增量 |
|---|---|---|
| `retriever.search` | 12.40 ms | — |
| `api.recall` | 23.56 ms | **+11.2 ms** |
| `rpc` 往返（stdio NDJSON，真实子进程） | 24.82 ms | **+1.3 ms** |

进程边界（P2-2 的对象）只占 1.3 ms ≈ 5%。**RPC 不是我该优化的地方。**

### 1.3 两个决定性实验

**实验 A — KNN 耗时与候选集大小几乎无关（固定开销主导）**

| LIMIT k | 10 | 40 | 100 | 400 | 1060 |
|---|---|---|---|---|---|
| `_vector_knn` | 4.75 ms | 4.64 ms | 4.75 ms | 5.10 ms | 5.93 ms |

候选集放大 100 倍，耗时只涨 25%。

**实验 B — scope 前置过滤（v1 的 P0-1）实际收益**

| 查询可见集 | 绑定事实数 | KNN 耗时 |
|---|---|---|
| 无过滤（全库） | 1061 | 4.73 ms |
| scope 1 | 84 | 3.09 ms |
| scope 6 | 26 | 3.38 ms |
| scope 2 | 311 | 3.86 ms |

把候选从 1061 条砍到 26 条（**40 倍**），只省约 **1.3 ms**。且注意：**scope 过滤早已实现**
（见 `retriever._scope_predicate`，谓词同时传给两条腿），v1 把它列为待做项是事实性错误。

**实验 C — 固定开销的来源**

| 查询形态 | 耗时 |
|---|---|
| bare `vec0 MATCH`（无 join） | **2.43 ms** |
| `vec0 MATCH` + `fact_id IN (facts 子查询)` | 4.64 ms |

`sqlite-vec` 自身的暴力扫描（512 维 × 1072 行）就有 **2.4 ms 地板**，不随 LIMIT 变化；
facts 成员判定再加约 1.9 ms。

## 二、由数据得出的结论

1. **`_rerank` 优化（v1 的 P0-2 / P1-1）应当整体删除。** 实测 0.23 ms，占 1.8%。
   为它加物化列、索引、同事务更新与校验任务，是拿显著复杂度换不到 2% 的收益。
   v1 所称「O(候选) 的 Python 侧曲线计算」——O(候选) 是 58 条，不是五万条。
2. **`_scope_view` 缓存（v1 的 P1-4）无意义。** 实测 0.037 ms。
3. **查询嵌入缓存（v1 的 P1-2）被高估约一个数量级。** 单次 embed 1.51 ms；
   即便命中率 100% 也只省 1.51/12.40 ≈ **12%** 的 search，或 6% 的 recall。
   v1 自定验收线「命中率 ≥ 40%」对应端到端收益 **~2.4%**。
   不值得引入 W-TinyLFU + Count-Min Sketch + 频率衰减 + L2 落盘表。
4. **真正的瓶颈是 sqlite-vec 暴力 KNN（8.91 ms，72%），且其中 2.4 ms 是库自身地板。**
   KNN 是唯一随事实数增长的部分，v1 却把它排到 P3（>5000 条才做）。
5. **v1 完全漏掉了一个更大的目标：`api.recall` 比 `search` 多花 11.2 ms。**
   其中 `_load_conflicts` 实测 **6.4 ms**（扫全部 1061 条 active 事实 + 批量拉 fact_scopes 4.8 ms），
   而该库当前**冲突数为 0**——即每次 recall 付 6.4 ms 扫描，绝大多数时候一无所获。

## 三、新方案

排序原则：**按实测 ms 收益 / 实现复杂度 排序，不按理论优雅度排序。**

### P0：`_load_conflicts` 惰性化（唯一高收益低风险项）— ✅ 已实施

**实施结果（2026-09，`--repeat 30`，同一库）**：

| 指标 | 优化前 | 优化后 | 改善 |
|---|---|---|---|
| `api.recall` p50 | 23.56 ms | **15.71 ms** | **−33.3%** |
| `api.recall` p95 | 26.40 ms | **20.52 ms** | **−22.3%** |
| RPC 往返 p50 | 24.82 ms | **16.24 ms** | **−34.6%** |
| `retriever.search` | 12.40 ms | 12.83 ms | 不变（未触及） |

超出验收目标（≤17 ms）。`conflicts` 字段仍在响应契约中，语义不变。

**最终实现（保留字段 + 惰性，而非删除）**：`recall` 仍返回 `conflicts`，
但扫描被 `_has_conflict_candidate` 前置门控——一个**廉价的必要条件**。

关键推理（这是整个改动成立的基础）：把行按 `(subject, predicate)` 分组但
**不看 scope**，若没有任何键持有 ≥2 个不同 object，则任何尊重 scope 的分组
都不可能找到冲突——因为按 scope 切分只会在 `(subject, predicate)` 组内**再细分**，
两件共享 scope 集的事实必然共享该键，反之不成立。所以：

- 门控返回 `False` 是**缺席的证明**，提前返回绝不会漏报冲突；
- 门控返回 `True` 是**不确定**（两个 object 可能分处不同 scope，那不算冲突，
  即设计里的"跨作用域 + 矛盾 → 不判矛盾"），因此必须落到完整扫描再判。

**实测**：干净库上 `_load_conflicts` 从 6.4 ms 降到 **~1.8 ms**
（剩余的是共享的那一次行读取），冲突存在时行为与原先完全一致。

**验证**：全量 `pytest` **600 passed, 1 skipped**；新增 3 个门控专项测试
（干净库短路 / 跨 scope 时必须下沉 / 多值键不武装门控），
并做了**双向验证**：把门控改成恒 `False` → 3 个测试失败（含 2 个原有冲突测试）；
改成恒 `True` → 2 个新测试失败。两个失败方向由不同测试捕获，
证明门控在两个方向上都真正受约束，而非"恰好通过"。

**放弃的备选**：直接删除 `conflicts`。虽然已核实 `dsh/src/tools.ts:982` 的
`memory_recall` 只读 `r.facts`、host 侧无消费者，但 `api.recall` 是公开 API 且
docstring 明确列出该字段，删除属破坏性变更；惰性化达到同等收益（−33%）且零破坏。

### P1：削减 KNN 的 facts 成员判定开销（约 1.9 ms）— ❌ 已验证并回滚

**结论：不应实施。原实现（SQL `IN` 过滤）已经是最优形态。**

**实测确认的机制**（`EXPLAIN QUERY PLAN` + 逐项计时）：vec0 的 KNN 扫描本身约
2.4–2.6 ms 固定开销，与 LIMIT 基本无关（LIMIT 10→1081 只从 2.46→3.81 ms）。
但 rowid 的 `IN` 过滤**按列表基数计价**：`IN(1)`=2.5 ms、`IN(500)`=3.8 ms、
`IN(1081)`=5.6 ms；匹配不到任何行（`IN('zzz_none')`=2.5 ms）与无谓词相同——
说明成本来自列表大小本身，而非过滤掉了多少结果。字面量列表与子查询形式耗时相同
（4.59 vs 6.47 ms），所以瓶颈不是子查询/bloom filter。

**于是尝试改为 Python 侧成员过滤**（取更深、再筛，避开 `IN` 的基数定价）：

- 健康库上**确实更快**：5.13 → 3.19 ms（省 ~1.9 ms），且 192 组
  （query × pool × max_distance）组合逐一比对，**零差异**。
- 但在「某用户的 active 事实只占向量表一小部分」的多用户库上**灾难性退化**。
  为凑够 pool 必须反复全表扫描：

  | 场景 | 旧（SQL IN） | 新（Python 过滤） |
  |---|---|---|
  | active=10, noise=2000 | 4.38 ms | **47.67 ms** |
  | active=50, noise=2000 | 4.21 ms | **56.94 ms** |

  结果仍然正确（逐 id 比对一致），但这是**纯性能回退**，最坏 13.5 倍。
- 改用「单次固定深度取深再筛」（不做递进）同样不行：比旧实现更慢
  （4.98 vs 4.12 ms）**且结果不完整**（漏 id，`complete=False`）。

**根因**：`IN` 虽按基数计价，但它把过滤**下推到同一次扫描内**；
取深再筛则把「过滤」变成「多扫几遍」，在成员稀疏时后者远贵于前者。
成员判定那 1.9 ms 是 vec0 的既定成本，不是可回收的浪费。

**副产品（值得单独修的真实缺陷）**：探查中触发 sqlite-vec 的硬限制——
k 值上限 4096，超过会报 `k value in knn query too large`。该错误被
`_vector_knn` 的 `except sqlite3.Error` 吞掉，**静默返回空**，只在
`last_degraded` 里留一个 `vector`。也就是说若 pool 配置得过大
（`candidate_pool_multiplier * top_k > 4096`），语义检索会无声失效。
当前默认配置（4 × 10 = 40）远低于上限，故未暴露，但值得加一道
参数校验或让降级更显眼。见下文 P1b。

### P1b：vec0 的 k 上限防护 — ✅ 已实施

**问题（在 P1 的探查中意外发现）**：`sqlite-vec` 对 KNN 的 `k` 有硬上限，
超过就**报错而非钳制**。实测阈值精确在 **4097**：`k=4096` 正常返回，
`k=4097` 抛 `k value in knn query too large`。

危险之处不在限制本身，而在失败的形态：该异常被 `_vector_knn` 的
`except sqlite3.Error` 吞掉，**返回 `[]`**，只在 `last_degraded` 里留一个
`vector`。也就是说过大的 pool 会**静默删掉语义检索这一半**，让召回退化为
纯 FTS——仍然能回答，只是更差，而 host 侧根本不读 `degraded`
（`memory_recall` 只读 `r.facts`），没有任何可见症状。

而 pool = `top_k * candidate_pool_multiplier`，**纯靠配置即可触发**
（`top_k=2000` + 出厂倍数 4 = 8000）。

**改动**（`retriever.py`，+31 行）：新增 `VEC_MAX_K = 4096` 常量，
在 `_vector_knn` 内钳制并记 warning；同时对 `k <= 0` 直接返回空
（`LIMIT 0` 是白跑一趟，负值会让驱动报错，两者都不是查询）。

**为什么钳制而不是报错**：要求比引擎能排序的还多的邻居是部署配置错误，
返回引擎支持的最深排序，比返回空更接近调用方的本意。

**实测**：`k=4097`/`k=5000` 从「返回 0 条」变为「返回 1087 条」；
过限配置下 `_vector_knn` 返回 1087 条且 `last_degraded == []`。

**验证**：全量 `pytest` **603 passed, 1 skipped**（+3 个新测试），
并做双向验证：去掉钳制后
`test_vector_knn_clamps_a_pool_above_the_engine_ceiling` 失败，
报错正是它要防的那条 `k value in knn query too large`。
健康路径延迟无变化（RPC 往返仍 16.4 ms）。

### P2：查询嵌入缓存（降级为简单实现）

**重新定位**：不是「单点收益最大」，而是**12% 的 search / 6% 的 recall**。

**若仍要做**，用最简形式，**不要 W-TinyLFU**：
- 内存 LRU（容量几百条即可）+ 可选落盘表 `query_embed_cache(query_hash, model_version, embedding, ts)`。
- 失效挂 `model_version`，与事实写入无关（这一点 v1 判断正确，保留）。
- 理由：实测 embed 1.5 ms，且查询文本访问模式与 jieba 分词同源（同一批 query 文本），
  v1 给二者分别指定 W-TinyLFU 与 LRU 缺乏依据。这类小容量缓存上，
  算法差异远小于参数噪声。

**收益上限**：命中率 40% 时端到端省约 0.6 ms（recall 口径）。

### P3：规模扫描 — ✅ 已完成（结论：**当前不该做优化，而该及早排气/换依赖**）

用 `bench/scale_scan.py` 在合成库（512 维真实随机向量，与生产同一 `_vector_knn`
调用、同 scope 过滤、pool=40）上扫描。**结论推翻了本方案原先的假设**。

#### 实测：精确 KNN 是超线性退化，不是「1 万条才显著」

| facts | `_vector_knn` p50 | p95 | raw vec0（无过滤） | FTS p50 | 库大小 |
|---|---|---|---|---|---|
| 1,000 | 3.36 ms | 3.42 ms | 1.53 ms | 0.01 ms | — |
| 2,500 | 8.39 ms | 8.60 ms | 3.73 ms | 0.01 ms | 7.4 MB |
| 5,000 | 16.20 ms | 16.32 ms | 6.67 ms | 0.01 ms | 12.3 MB |
| 10,000 | 54.74 ms | 57.16 ms | 22.46 ms | 0.06 ms | 24.3 MB |
| 20,000 | **110.67 ms** | 114.14 ms | 46.54 ms | 0.03 ms | 48.3 MB |

**每千条成本**：1k–5k 稳定在 3.2–3.4 ms/1k（近似线性），**10k 时跳到 5.47 ms/1k**，
20k 时 5.53 ms/1k。即 **5k 之后有一个明显的恶化拐点**（约 12 MB 库 / 6k 向量，
形态上像缓存容量悬崖），20k 是 20 倍规模、33 倍耗时。

线性外推（**仅数量级参考**）：≈4,500 条达 20 ms、≈9,600 条达 50 ms、
≈18,200 条达 100 ms。

**所以原方案写的「>5000 条才启动 ANN」严重低估**：5000 条时已经 16.2 ms，
而当前生产库（1061 条）是 9 ms——**离 20 ms 的门槛只剩约 4 倍余量**。

#### 关键：这个依赖根本没有 ANN 可用

按计划「届时可选 HNSW / 分区索引」，实测**全部不可用**：

```
CREATE VIRTUAL TABLE t USING vec0(a float[4], index=hnsw)   -> Unknown table option: index
CREATE VIRTUAL TABLE t USING vec0(a float[4], partitions=16) -> Unknown table option: partitions
```

本项目 pin 的 **sqlite-vec v0.1.9 不含任何 ANN 索引**，也不导出建索引的函数
（`pragma_function_list` 只有量化/距离/算术）。**「换 ANN」在这个依赖上不是一个
可以执行的方案**，只有量化这一条路。

#### 量化粗筛→精排：实测不可行

唯一可用的杠杆是 `vec_quantize_binary` + `bit[N]` 列。20k 条实测：

| 粗筛深度 M | recall@40 | 粗筛耗时 | 重排耗时 |
|---|---|---|---|
| 100 | 32.5% | 2.72 ms | 60.32 ms |
| 400 | 45.0% | 7.77 ms | 96.28 ms |
| 1,000 | 72.5% | 20.43 ms | 165.30 ms |
| 2,000 | 82.5% | 21.63 ms | 279.87 ms |
| 4,000 | 92.5% | 29.28 ms | **532.70 ms** |

粗筛本身确实快（7.15 ms vs 精确 45.26 ms，**6 倍**），但：

1. **召回太差**。深度 4000 仍丢 7.5%，而 512 维下单比特量化信息损失本就大。
2. **重排把收益全吃掉**。深度 1000 时总成本 ~186 ms，**是精确基线 45.9 ms 的 4 倍**。

#### 根因：瓶颈是 blob I/O，不是距离计算

重排为什么这么贵？实测（20k 条，候选数 M）：

| M | 读取量 | 耗时 |
|---|---|---|
| 100 | 0.2 MB | 21.45 ms |
| 400 | 0.8 MB | 24.29 ms |
| 1,000 | 2.0 MB | 99.45 ms |
| 2,000 | 4.1 MB | 193.01 ms |
| 5,000 | 10.2 MB | 500.85 ms |

且两种完全不同的距离实现耗时几乎相同：
`vec_distance_cosine` 170 ms vs **Python 手写余弦 193 ms**——说明贵的不是算距离，
而是**把 2048 字节/条的 float32 blob 读回来**。

这解释了 `IN` 过滤那 85 ms 的额外开销（P1 里没查清的那部分）：它同样是逐行读 blob。
也解释了为什么 P1 的「取深再筛」在大库上崩掉——每种变形都在重复读同一批 blob。

**推论**：任何「粗筛 + 精排」设计，只要精排要读回 float32 blob，就会继承同一笔
I/O 成本。在 512 维 float32 上，**这个方案族整体不成立**。

#### P3 的结论与建议

**当前不要做 P3 的工程改造**，因为：
1. 唯一可用的加速手段（量化粗筛）实测**比精确检索更慢且损失召回**；
2. 唯一有效的方向（真 ANN）在当前依赖上**无 API 可用**。

**该做的是两件更便宜的事**：

- **设定并监控规模阈值**。按实测，把告警线定在 **3,000–5,000 条**
  （对应 8–16 ms），而不是原来的 5,000 条「才启动优化」。
  `metrics`/`stats` 已经能报事实数，接一条阈值告警即可，成本接近零。
- **把「换依赖」提前论证，而不是等撞墙**。若事实规模会长期增长，
  需要先验证 `sqlite-vec` 新版本（或 `sqlite-vec` 之外的后端）是否提供
  真正的 ANN，以及迁移代价。这是一个**依赖选型**决策，不是读路径优化。
  在它落地前，任何 KNN 微优化都只是推迟撞墙时间。

**触发条件（修正版）**：事实数 > 3,000 时启动「依赖选型」调研；
> 10,000 时它就从「调研」变成「必须做」——那时 KNN 已占召回延迟的绝大部分。

**决策依据必须是 benchmark 数据，不是 v1 里那个凭空的「5000 条」阈值。**

### 不做（明确排除）

| v1 项目 | 排除理由（实测） |
|---|---|
| P0-1 scope 前置过滤 | 已实现；且 40 倍缩小候选只省 1.3 ms |
| P0-2 物化重排序键 | `_rerank` 仅 0.23 ms |
| P1-1 两级重排 | 同上，且会改动排序语义 |
| P1-2 W-TinyLFU | 用简单 LRU 即可，收益上限 12% of search |

## 四、测量方法（可复现）

```bash
python bench/stage_timing.py --repeat 40     # 单库分阶段归因
python bench/scale_scan.py --sizes 1000,2500,5000,10000,20000
```

`stage_timing.py` 做四件事，缺一不可：

1. **分阶段**：直接调用 retriever 各内部阶段，逐个计时（含 `rrf_merge`/`_fetch_facts` 等被忽略的胶水）。
2. **整体校验**：单独测 `search_total`，与分阶段之和对比，差额即未归因胶水（实测 3.6%）。
3. **端到端**：起真实 `AtomMem` 测 `api.recall`，暴露 `search` 之外的开销
   （**正是这一步发现了 6.4 ms 的 `_load_conflicts`**）。
4. **真实进程边界**：spawn 真实 `python -m atom_memory.rpc`，按 NDJSON 协议计时往返。

`scale_scan.py` 用合成库扫描规模曲线，测**同一个 `_vector_knn`**，
并同时报 raw vec0（剥离成员判定）与 FTS，用来区分「扫描本身」和「过滤」的成本。

注意事项（踩过的坑，写进 harness 注释）：
- **必须预热模型**：首调用 embed 约 43 ms，是冷启动，混入稳态会把 embed 高估 30 倍。
- **子进程 stderr 不能用未抽干的 PIPE**：child 往 stderr 打日志，管道缓冲区（~64 KB）满后
  child 永久阻塞，表现为「RPC 极慢」的假象。重定向到文件。
- **测 p50 与 p95**，并固定重复次数，避免把偶发抖动当结论。

## 五、落地顺序

```
P0  _load_conflicts 惰性化（6.4 ms）  ← ✅ 已完成，recall p50 23.6 → 15.7 ms（−33%）
        ↓
P1  KNN 成员判定（~1.9 ms）          ← ❌ 已验证并回滚：为 1.9 ms 换来最坏 13.5 倍退化
        ↓
P1b vec0 k 上限防护                   ← ✅ 已完成，消除一条静默失效路径
        ↓
P2  查询嵌入缓存（简单 LRU，~0.6 ms）← 可选，收益小
        ↓
P3  规模扫描                          ← ✅ 已完成：拐点在 5k，当前依赖无 ANN，量化粗筛实测更慢
        ↓
P4  依赖选型调研（sqlite-vec 是否有真 ANN / 换后端）← 事实数 > 3,000 时启动
```

**读路径优化到此为止。** 当前延迟构成（P0/P1b 之后）：`_vector_knn` 9.06 ms 占 72%，
其中约 2.4 ms 是 `sqlite-vec` 的固定地板；剩下的全是逐行读 2048 字节 blob 的 I/O，
**已证无法通过改写 SQL 消除**（P1、P3 两次独立验证）。下一步不是优化，而是
**规模监控 + 依赖选型**。

每一项独立可回滚；每一项落地后重跑 `stage_timing.py`，用**同一口径**确认收益，
而不是靠推理相信它变快了。

## 六、与 v1 的关系

**保留**：一致性设计原则（缓存挂版本号、物化列与 facts/fts/vec 同事务）、
「每阶段独立可回滚」、ANN 用 benchmark 决策的方法论。这些工程判断是对的。

**推翻**：优化对象的选取。v1 把 96% 的篇幅投在占 1.8% + 0.3% 延迟的两个阶段上，
同时漏掉了占 27% 的 `_load_conflicts`，并把唯一的真瓶颈（KNN）排到最后。
根因是**先有结论、后找证据**——「scope 顺序错了」「缓存单点收益最大」都是未经测量的断言。

**本轮又推翻了本方案自己的 P3 假设**：v2 原写「>5000 条才启动 ANN」，
实测 5k 时已 16.2 ms 且拐点就在 5k 之后；更关键的是，
「换 ANN」在当前 pin 的 sqlite-vec v0.1.9 上**根本没有 API**。
这提醒了同一件事：**连自己写的阈值也必须验证**。

**方法论修正**：先跑归因，再定方案。任何优化项在动工前，必须能回答
「它实测占多少 ms」，否则它就是一个假设，不是一项优化。
本轮 P1 和 P3 都是"看起来该做、实测不该做"的例子，且都由测量推翻——
**这正是先测量再动手的价值所在**。
